# Rate Limiting 정책

> 사용량 한도는 비용([[domain/AI비용관리정책]])과 가용성([[domain/AI서비스SLA와가용성]])을 지키는 장치다. 이 페이지는 단위별 한도 설계, 교실 동시 접속, 사용자 안내, 업체 한도 대응을 다룬다.

## 핵심 요약

- 한도는 **누구에게(사용자·기관·API 키·IP)**, **무엇을(요청 수·토큰 수·동시 연결)**, **어떤 시간 창으로(순간 버스트·지속)** 거는지 세 축으로 정한다.
- HTTP **429 Too Many Requests**는 일정 시간 동안 요청이 너무 많을 때 쓰는 상태 코드이고, 응답에 **Retry-After** 헤더로 다시 시도할 시점을 알려 줄 수 있다. 429 응답은 캐시하면 안 된다 (RFC 6585 4절, https://www.rfc-editor.org/rfc/rfc6585#section-4). [verified 2026-10-12] Retry-After 형식(초 또는 HTTP 날짜)은 RFC 9110 10.2.3절에 정의된다 (https://www.rfc-editor.org/rfc/rfc9110#section-10.2.3). [verified 2026-10-12]
- 교육 서비스의 특수성은 **교실 단위 동시 시작**이다. 수업 시작 종이 울리면 한 반 30명이 같은 초에 같은 기능을 누른다. 사용자 단위 한도만으로는 기관 전체 폭주를, 기관 단위 한도만으로는 한 반의 독점을 막지 못한다.
- 시험·평가 기능은 **우선순위 등급**을 두어 일반 기능보다 먼저 처리한다.

## 상세

### 한도 단위

| 단위 | 목적 | 예 [가정: 수치는 부하 시험으로 확정] |
|------|------|------|
| 사용자 | 개인 남용·반복 재생성 방지 | 분당 요청 수, 일 크레딧 |
| 학급 | 한 반이 기관 한도를 독점하지 않게 | 학급별 동시 처리 수 |
| 기관(학교·학원·기업) | 계약 포함량, 공정 배분 | 월 토큰, 동시 연결 |
| API 키(파트너 연동) | 연동 오류·폭주 차단 | 키별 초당 요청 |
| IP | 비로그인 남용·봇 차단 | 학교는 공용 IP(NAT)라 IP 한도를 낮게 잡으면 학교 전체가 막힘 |

- **학교 NAT 주의**: 한 학교 전체가 같은 공인 IP로 나오는 경우가 많다 [가정]. IP 한도는 인증 사용자에게는 완화하고 비로그인 엔드포인트에만 엄격히 건다.

### 요청 한도 vs 토큰 한도

| 방식 | 장점 | 단점 |
|------|------|------|
| 요청 수 | 이해·안내가 쉬움 | 긴 요청 하나가 큰 비용 |
| 토큰 수 | 비용과 직결 | 사용자가 예측하기 어려움 |
| 혼합 | 요청 수로 안내, 토큰으로 내부 보호 | 구현 복잡 |

- 학습자에게는 "오늘 질문 N회 남음"처럼 요청 단위로 보여 주고, 내부에서는 요청당 최대 토큰을 함께 제한하는 혼합형이 흔한 선택이다 [가정].

### 버스트와 지속

- 토큰 버킷 방식: 버킷 크기 = 허용 버스트, 채워지는 속도 = 지속 한도. 수업 시작 버스트를 받아 주되 지속 남용은 막는다.
- **교실 피크 완화**: 수업 시작 시 첫 화면을 AI 호출 없이 시작(문제 읽기 → 시도 → 튜터)하게 설계하면 요청이 자연스럽게 분산된다. 교사용 "반 전체 생성" 기능은 대기열로 순차 처리한다.
- **학기초·개학 첫 주**: 가입·레벨 테스트·첫 사용이 몰린다 ([[domain/학사일정]]). 사전 증설과 한도 임시 상향 계획을 세운다.

### 우선순위 등급

| 등급 | 기능 | 처리 |
|------|------|------|
| P0 | 시험·평가 중 기능, 제출 연계 | 전용 용량, 한도 예외 |
| P1 | 수업 중 튜터, 교사 실시간 기능 | 일반 한도, 대기열 우선 |
| P2 | 자료 생성, 리포트 | 혼잡 시 지연 허용 |
| P3 | 배치·백그라운드 | 야간 처리 |

### 한도 안내 (UI·API)

- 사용자 화면: 남은 횟수 미리 표시, 초과 시 "N분 후 다시 질문할 수 있어요" + 대안(교재 해설 보기, 선생님께 질문). 오류처럼 보이지 않게 쓴다. 아동용은 쉬운 말로.
- 교사 화면: 학급 사용량, 기관 포함량 잔여, 혼잡 안내.
- API: 429 + Retry-After, 응답 본문에 한도 종류와 재시도 시점. 파트너에게 지수 백오프와 지터를 권장하는 문서를 제공한다.
- 남은 한도 헤더(관행적으로 RateLimit 계열 헤더)는 표준화 진행 중이므로 채택 전 최신 규격을 확인한다 [확인 필요: IETF 초안 상태].

### 남용 방지

- 자동화 스크립트·계정 공유로 인한 과사용 탐지 ([[domain/부정수강방지]]), 프롬프트 주입·탈옥 반복 시 단계적 제한 (A14).
- 한도 우회 시도(다중 계정)는 기관 단위 합산으로 막는다.

### 업체 한도 대응

- 클라우드 LLM 업체는 계정·모델별로 분당 요청·토큰 한도를 둔다 [확인 필요: 업체별 수치·상향 절차]. 우리 한도 합계가 업체 한도를 넘지 않게 설계하고, 피크 전 상향 신청 리드타임을 일정에 넣는다.
- 업체 429를 받으면 즉시 재시도하지 말고 대기열·대체 경로로 보낸다 ([[domain/AI서비스SLA와가용성]]).

## 에듀테크 맥락

- **미성년**: 한도 초과 화면이 처벌처럼 느껴지지 않게 하고, 학습 흐름(문제 풀이·제출)은 한도와 무관하게 동작하게 한다.
- **학생 평가**: 시험 중 한도 초과는 공정성 문제다. 평가 기능은 P0로 분리하고 사전 부하 시험을 한다.
- **고객 요구**: 학교·교육청은 동시 접속 인원 보장을, 기업은 부서별 할당과 사용량 리포트를, 연동 파트너는 명확한 한도 문서를 요구하는 경우가 많다 [가정].

## 방식별 차이

| 방식 | 한도 관점 |
|------|-----------|
| 규칙·NLP | 한도 거의 불필요, 혼잡 시 대체 경로 |
| RAG | 검색 단계도 한도 대상(벡터 DB 처리량) |
| 로컬 LLM | GPU 동시 처리 수가 물리적 한도. 대기열 설계가 핵심 |
| 클라우드 LLM | 업체 한도가 상한. 계정 분리·상향 신청 |

## 에듀테크 PM 적용

- [ ] 단위(사용자·학급·기관·API 키·IP)별 한도와 근거를 P09에 적는다
- [ ] 요청·토큰 혼합 방식과 요청당 최대 토큰을 정한다 (A12)
- [ ] 수업 시작·학기초 피크 시나리오로 부하 시험을 한다 (B06, A13)
- [ ] 우선순위 등급과 평가 기능 전용 용량을 정한다 (P09, A11)
- [ ] 한도 초과 화면 문구(연령별)와 대안 경로를 E10에 넣는다
- [ ] API 429·Retry-After 응답 형식과 파트너 문서를 만든다 (B03)
- [ ] 업체 한도·상향 리드타임을 피크 일정에 반영한다 (M02)

**관련 산출물**: P09(주), A12, A13, A11, A14(탈옥 반복 시 제한), P08(안전 기능은 한도 예외), P07(한도·하향 고지), E13(로그 최소화), B03, B06, E10, M02.

## 흔한 오해

- "IP당 한도면 충분" — 학교 NAT에서는 학교 전체가 막힌다.
- "한도는 남용자만 걸린다" — 설계가 틀리면 수업 시작마다 선량한 학생이 걸린다.
- "429면 바로 재시도" — 폭주를 키운다. Retry-After와 백오프를 지킨다.
