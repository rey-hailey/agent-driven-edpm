# L06 수료증·크레덴셜설계서

> **작성 가이드**
> - **목적**: 수료 확정(L03 CP) 이후 어떤 증명을 어떤 형식으로 발급하고, 제3자가 어떻게 진위를 확인하며, 디지털 배지·검증 가능한 자격증명·블록체인을 쓸지 정합니다.
> - **입력**: L03 수료 규칙(CP), L01 과정·트랙, L05 연동(HRIS 회신), E13 개인정보, [[domain/수료증과디지털크레덴셜]]
> - **게이트**: L03이 `done`이어야 합니다. 발급 조건은 L03 CP를 그대로 참조하고 여기서 새로 정의하지 않습니다. 법정 서식이 필요한 수료증(환급 과정 등)은 `[확인 필요]`로 두고 원문 대조합니다.
> - **적용 유형**: AT01, AT02, AT03, AT08, AT09 필수 / AT04, AT07 해당 시 / AT05, AT06, AT10 대부분 선택 또는 `n/a`
> - **검토 패널 (권장)**: 운영 매니저, 디자이너, 보안 담당, B2B HRD 담당, 법무
> - 표의 첫 행은 예시 서비스 **스킬업**(성인 대상 VOD + 라이브 강의 마켓플레이스, 강사 입점·수익배분, 기업 B2B 좌석 판매, 일부 사업주 환급 과정) 기준입니다.

## 1. 발급 대상과 트리거

| 증명 종류 | 발급 조건 (L03) | 트리거 | 형식 | 예시 |
|-----------|-----------------|--------|------|------|
| 과정 수료증 | CP-01 / CP-02 | 수료 배치 확정 | PDF + 검증 URL | CRS-01 수료 (CP-01) |
| 트랙 수료증 | 트랙 내 모든 과정 수료 | 마지막 과정 수료 확정 | PDF + 배지 | {} |
| 환급 과정 수료증 | CP-03 | 확정 후 {검토} | 법정 서식 [확인 필요] | {} |
| 참여 확인서 | {수료 미달이지만 참여 증명} | 요청 시 | PDF | {} |
| 디지털 배지 | {} | {} | Open Badges 3.0 | {} |

## 2. 수료증 필드

| 필드 | 필수 | 출처 | 공개 검증 페이지 노출 | 예시 |
|------|:---:|------|:---:|------|
| 증명서 번호 | 필수 | 발급 시 생성 (추측 불가 난수 포함) | 예 | SU-2027-0001-{난수} |
| 수료자 이름 | 필수 | 계정 | 예 (마스킹 선택) | 홍*동 |
| 과정명·과정 ID | 필수 | L01 | 예 | SQL 실무 데이터 분석 (CRS-01) |
| 학습 시간 | 필수 | L01 총 학습 시간 | 예 | 6시간 |
| 수료일 | 필수 | L03 판정일 | 예 | 2027-04-20 |
| 수료 기준·rule_version | 선택 | L03 | 아니오 | CP-01 v1 |
| 성적 | 선택 | L04 | 수료자 선택 시 | {} |

| 생년월일 등 추가 식별 정보 | 법정 서식 요구 시만 | [확인 필요] | 아니오 | {} |

## 3. 진위 확인

| 방식 | 동작 | 장점 | 한계 | 우리 선택 |
|------|------|------|------|-----------|
| 검증 URL·QR | 번호로 발급 기록 조회 | 단순, 누구나 확인 | 우리 서비스가 살아 있어야 함 | {채택/보류} |
| 서명된 PDF | 전자서명으로 위변조 탐지 | 오프라인 확인 | 서명 인증서 관리 | {} |
| Open Badges 3.0 | 표준 배지, 지갑·SNS 공유 | 이식성, 메타데이터 풍부 | 수용처 인지도 [확인 필요] | {} |
| W3C Verifiable Credentials | 발급자 서명, 보유자 지갑, 검증자 직접 확인 | 서비스 종료 후에도 검증 가능 | 지갑 생태계·키 관리 부담 | {} |
| 예시 (스킬업) | 검증 URL 채택, Open Badges 3.0은 트랙 수료부터 [가정] | | | |

검증 페이지는 무차별 조회를 막기 위해 번호에 난수를 포함하고 조회 빈도를 제한합니다.

| 질문 | 예/아니오 | 메모 |
|------|:---:|------|
| 발급 기관이 사라져도 검증이 반드시 필요한가 | {} | VC로 대부분 해결 가능 |
| 여러 기관이 공동 발급·상호 검증하는 구조인가 | {} | {} |
| 수용처(채용사·기관)가 블록체인 검증을 요구하는가 | {} | [확인 필요] |
| 체인에 개인정보를 올리지 않는 설계(해시만)가 가능한가 | {} | 삭제권과 충돌 검토(E13) |
| 운영 비용·키 관리를 감당할 수 있는가 | {} | {} |
| 판정 | {쓰지 않음 / 해시 앵커링만 / 사용} | 예시: 쓰지 않음 [가정] |

## 5. 발급 운영

| 항목 | 규칙 | 예시 |
|------|------|------|
| 발급 시점 | 수료 확정 후 {N}시간 내 | 24시간 [가정] |
| 이름 변경·재발급 | 본인 확인 후 재발급, 구 번호 무효 표시 | {} |
| 취소 | 부정 확정(P03) 시 취소, 검증 페이지에 "취소됨" 표시 | {} |
| 환불과의 관계 | 수료 후 환불 시 취소 여부 (P01) | P01 규칙 따름 |
| B2B 회신 | 수료 데이터 HRIS 전송 (L05) | 일 1회 |
| 보존 | 발급 기록 보존 기간 | [확인 필요] |
| 디자인 | 템플릿 버전, 공동 브랜드(B2B) | 기업 로고 병기 옵션 |

## 완료 체크리스트

- [ ] 증명 종류마다 발급 조건이 L03 CP를 참조한다 (새 정의 없음)
- [ ] 수료증 필드와 공개 검증 페이지 노출 범위가 정해졌다
- [ ] 진위 확인 방식이 선택되고 조회 남용 방지가 있다
- [ ] Open Badges 3.0·VC 채택 여부와 이유가 있다
- [ ] 블록체인 선택 기준 질문에 답하고 판정이 있다
- [ ] 재발급·취소·환불 연동 규칙이 P01·P03과 일치한다
- [ ] 법정 서식·보존 기간에 `[확인 필요]`와 담당이 있다
