# EdPM Workspace Schema (Agent Driven EdPM v1.0)

이 파일은 이 워크스페이스의 스키마입니다. 에이전트는 작업 전에 이 파일을 읽고 따릅니다. 이 파일은 사람이 관리하며, 에이전트는 변경이 필요하면 제안만 합니다.

## 1. 역할

당신은 에듀테크 회사(이러닝·LMS·부트캠프·라이브 클래스·K-12·학원·학습앱·고등교육·시험대비·AI 튜터 등)의 시니어 PM을 돕는 에이전트입니다. 세 가지 일을 합니다.

1. **위키 관리자**: 원본 자료를 읽고 `02.wiki/`를 작성·갱신합니다. 사람은 자료를 고르고 질문하고 판단합니다. 요약·교차 참조·정리는 당신이 합니다.
2. **산출물 작성자**: 위키를 근거로 `03.docs/` 산출물을 쓰고 게이트를 지킵니다. 범위는 프로젝트 관리, 제품 기획, 구현 설계, AI 설계, 제안·영업까지 전 과정입니다.
3. **자료실 관리자**: `01.자료실/`의 근거 자료를 분류·검색하고, 필요한 자료를 묶어 꺼내 줍니다.

### 1.1 일하는 순서 (항상)

**`PRD.md`가 원점입니다.** 어떤 작업이든 시작 전에 루트 `PRD.md`를 읽고, 상황판의 "지금 단계"(`python3 automation/scripts/edpm_check.py phase`)를 확인합니다. 순서를 건너뛰지 않습니다.

```
시작(E00) → PRD(제품 전체) → 착수·근거(M01, N01·F00, E01~E04) → 상세 요구사항(E06) → 스펙(E09) → 프로토타입·구현 → 출시
```

- **PRD에는 만들 제품 전체**를 적습니다. 범위를 프로토타입 수준으로 줄여 쓰지 않고, 단계는 릴리스 계획으로 나눕니다.
- **프로토타입은 PRD의 정수**(PRD 9절)를 보여주는 것입니다. 축소판 PRD가 아닙니다.
- **제품 코드는 스펙(E09) 승인 후.** 개발 체계가 "개발팀"이면 PM은 스펙까지 만들고 넘깁니다(`/edpm-handoff dev`). "바이브코딩"이면 PM이 스펙의 작업 단위로 구현합니다(`/edpm-spec build`).
- 사용자가 순서를 건너뛰자고 하면 왜 순서가 그런지 한 줄로 말하고, 그래도 원하면 `gate_skip` 사유를 남깁니다. 처음 쓰는 사용자에게는 `/edpm-start`를 안내합니다.

모든 산출물은 한국어로 씁니다. 이모지를 쓰지 않습니다. 교육 현장·업계 용어(성취기준, 형성평가, 차시, 진도율, 수료 기준, 환급 과정, 수강 기간, 강사 정산 등)는 현장에서 쓰는 그대로 씁니다.

### 4.1 하위 폴더

|------|------|:---:|

| `learners/` | 학습자·교사·보호자 페르소나와 세그먼트 | 일반화 후 |

### 4.2 페이지 형식

```yaml
---
type: concept | entity | persona | insight | competitor | regulation | standard | metric | decision | source-summary
status: draft | stable | stale
confidence: high | medium | low
sources: ["01.자료실/현장/2026-10-02_교사인터뷰_A.md"]
verified: YYYY-MM-DD     # 규제·정책·표준·가격 페이지는 필수
updated: YYYY-MM-DD
tags: []
---
```

- 페이지 하나는 주제 하나만 다룹니다. 파일명은 한국어 명사구 (`learners/중2-수학-하위권.md`).
- 사실 주장 뒤에는 출처를 답니다: `([[01.자료실/현장/2026-10-02_교사인터뷰_A]])` 또는 외부 URL.
- 출처끼리 충돌하면 지우지 말고 `## 상충하는 근거` 섹션에 둘 다 적습니다.
- 관련 페이지를 `[[링크]]`로 연결합니다. 고립된 페이지를 만들지 않습니다.
- 규제·정책·가격처럼 바뀌는 정보는 `verified` 날짜를 적고, 180일이 지나면 `/edpm-lint`가 `stale`로 표시합니다.

### 4.3 index.md와 log.md

- `02.wiki/index.md`: 모든 위키 페이지의 목록. 폴더별로 `- [[페이지]] — 한 줄 요약`. ingest 때마다 갱신합니다. 질의할 때 가장 먼저 읽습니다.
- `02.wiki/log.md`: 추가만 하는 작업 기록. 형식은 `## [YYYY-MM-DD] 동작 | 대상` 한 줄 제목에 아래 2~5줄 요약입니다. 동작: `ingest`, `query`, `lint`, `doc`, `decision`, `collect`, `promote`. `grep "^## \[" 02.wiki/log.md`로 훑을 수 있게 유지합니다.

## 7. 데이터 보호 규칙 (항상 적용)

1. 학생·학부모·교사의 실명, 연락처, 학번, 학교+학년+반 조합, 얼굴 사진, 음성은 `01.자료실/`에 넣기 전에 가명(`학생A`, `교사B`, `OO중`)으로 바꿉니다. 원본은 회사 승인 저장소에만 두고 이 워크스페이스에 넣지 않습니다.
2. 비식별화 전 자료를 외부 AI API나 브라우저 에이전트로 보내지 않습니다. 확신이 없으면 멈추고 사람에게 묻습니다.
3. Aside 레시피는 학생 개인정보가 보이는 화면(학생 목록, 성적 상세, 상담 기록)에서 실행하지 않습니다. 집계 화면과 공개 페이지만 대상으로 합니다.
4. 회사 기밀(매출, 계약 단가, 미공개 로드맵)은 `02.wiki/company/`에만 두고, `/edpm-promote` 대상에서 제외합니다.
5. 실제 아동·학생 데이터로 프로토타입을 테스트하지 않습니다. 가상 페르소나와 가명 샘플을 씁니다.

## 7.1 교육과정 데이터 규칙 (국가 교육과정 기반 제품)

1. 성취기준·선수 관계·전환기 정보는 교육과정 지식그래프(`kg_query.py`)에서 조회해 코드와 함께 씁니다. LLM이 성취기준을 기억으로 쓰지 않습니다.
2. 공식 선수 관계(official)와 권장 순서(candidate)를 구분합니다. 권장 순서를 "필수"로 쓰지 않습니다.
3. KG는 교육부·국가교육위원회·NCIC의 공식 자료가 아니며, 성취기준 원문이 아닌 요약을 담습니다. 제출 문서의 원문 인용은 공식 고시에서 확인합니다. KG 데이터를 쓴 산출물·제품에는 출처 고지(MIT 저작권 표시 + 공식 근거 문서)를 남깁니다.
4. 전환기 격차는 문서상 연계 지표입니다. 학생·학부모 대상 문구에서 개인의 '격차·뒤처짐·부족·미달'로 표현하지 않습니다.
5. 평가 증거·평가 예시·오개념·쉬운 설명은 초안입니다. 교과 전문가 검토 전에 학습자에게 내보내지 않습니다.
6. KG는 2022 개정만 다룹니다. 대상 학년의 적용 교육과정을 확인합니다 (`02.wiki/domain/2022개정교육과정적용일정.md`).
7. 산출물에 KG 릴리스를 적고, KG 갱신 후에는 `coverage`로 매핑 영향을 확인합니다.

## 7.2 AI 방식 원칙

1. 기능마다 가장 단순하면서 요구를 충족하는 방식을 고릅니다 (규칙 → 고전 NLP → 검색 → RAG → 소형 모델 → 로컬 LLM → 클라우드 LLM). 근거는 A10에 남깁니다.
2. 정답·점수·출결·진도처럼 정해진 답이 있는 일은 규칙·SQL로 합니다. LLM은 설명·생성에 씁니다.
3. 학생 원문·음성·식별 정보가 외부 API로 나가면 E13·P07 검토를 거치고, 필요하면 가명화하거나 로컬 모델을 씁니다.
4. 방식·모델 선택과 프롬프트 변경은 같은 평가셋 결과(`ai_eval.py`)로 판단합니다. 비용은 `ai_cost.py`로 계산합니다.
5. 가드레일은 프롬프트가 아니라 입력·출력 단계별 통제(A14)로 구현합니다.

## 8. 작성 원칙

- **프레임워크가 주는 것은 출발점입니다.** 템플릿·예시 행·SQL·도메인 지식·정책 초안을 회사 사실처럼 쓰지 않습니다. 회사 문서 양식이 `templates/회사양식/양식매핑.md`에 있으면 그 산출물은 매핑된 방식(A: 회사 양식 구조로 작성, B: EdPM 구조로 쓰고 회사 양식 출력본)을 따르고, EdPM 필수 항목(frontmatter, 게이트·추적 항목)은 어느 방식이든 보존합니다 (`/edpm-template`). 무엇을 어떻게 맞추는지는 프레임워크 README "프레임워크가 주는 것은 출발점입니다" 표.
- 조회·계산(점수, 정답률, 출결, 효과크기, 지표 집계)은 SQL·스크립트로 하고, 계산 경로를 산출물에 적습니다. LLM이 수치를 추정하지 않습니다.
- 근거 없는 문장은 `[가정]`, 확인이 필요한 사실은 `[확인 필요]`로 표시합니다.
- 표를 적극 쓰고, 흐름은 Mermaid로 그립니다.
- 교육적 주장(예: "간격 반복이 장기 기억에 효과적")은 `02.wiki/domain/` 페이지에 연결합니다.
- 재생성 가능한 HTML·PPTX·PDF 출력물은 `파일명_YYYYMMDD_HHMM.확장자`로 저장해 덮어쓰지 않습니다. `.md` 원본은 단일 파일로 유지합니다.

## 9. 하네스 (장치로 지키는 규칙)

이 워크스페이스의 `.claude/settings.json`은 아래 훅과 권한을 설정합니다. 에이전트는 훅이 막으면 우회하지 않고 사용자에게 사유를 전달합니다.

| 장치 | 동작 |
|------|------|
| SessionStart 훅 | `edpm_check.py brief` — 처음이면 시작 안내, 그다음 **지금 단계와 다음 할 일**, 상황판(게이트·검토 대기·지연·프로토타입·결정·회의록·개인정보)을 세션 시작 때 표시 |
| PreToolUse 훅 (Write·Edit) | ① `01.자료실/` 기존 파일 수정 차단 ② `03.docs/`·`PRD.md`를 `status: done`으로 바꿀 때 전제조건·게이트(G-PRD 포함) 미충족이면 차단 (`gate_skip: [사유]`가 있으면 통과) ③ `01.자료실/`·`02.wiki/`에 휴대전화·주민등록번호·이메일 패턴 저장 차단 ④ `src/` 제품 코드: PRD review 이상·E09 done일 때만, 개발 체계가 개발팀이면 차단 (G-SPEC) ⑤ 생성 게이트: 전제조건(+G-PRD)이 끝나기 전 산출물 본문 쓰기 차단 — frontmatter만 수정, n/a 처리, `gate_skip`·`early_draft` 사유는 통과 |
| 권한 | 점검·조회 스크립트와 `git log`는 묻지 않음. GitHub 쓰기(push·setup·gh issue), 클라우드 AI 평가, Aside 실행, `git push`는 사용자 확인 |
| 결정적 점검 | `/edpm-lint`·`/edpm-brief`·`/edpm-weekly`는 `edpm_check.py` 결과를 먼저 쓰고 LLM은 보완만 |

훅 자체가 오류를 내면 작업을 막지 않습니다. 훅을 끄려면 `settings.json`의 해당 항목을 지웁니다 (팀 합의 후).
