# edpm-portfolio

포트폴리오가 보여줄 것은 **무엇을 만들었나보다 어떻게 판단했나**입니다. 채용하는 쪽은 "실제 구현에 이른 산출물, 그 과정의 문제 정의와 의사결정 이유, AI 결과물의 정확성을 어떻게 검증했는지"를 봅니다. EdPM 워크스페이스에는 이 기록이 이미 남아 있습니다: 산출물 frontmatter(상태·날짜), ADR(선택지·이유·예측·적중), 게이트 기록, `[가정]`·`[확인 필요]` 표시, 프로토타입 결정, 지표 계산 결과. 이 스킬은 그것을 뽑아 한 장으로 묶습니다.

원칙:
- **새 사실을 만들지 않습니다.** 수치·날짜·건수는 `edpm_check.py portfolio` 출력과 `/edpm-metrics` 결과만 씁니다. 기억이나 추정으로 성과를 쓰지 않습니다.
- **본인의 역할을 정확히.** 혼자 한 것, 함께 한 것, 남이 한 것을 구분합니다. 팀 성과를 개인 성과로 쓰지 않습니다.
- **실패와 빗나간 예측도 넣습니다.** 빗나간 ADR과 폐기한 프로토타입은 판단력을 보여주는 가장 좋은 재료입니다.
- **기밀은 밖으로 나가지 않습니다.** 결과물은 `05.outputs/portfolio/`에만 만들고, 외부 공유 여부는 사람이 정합니다. 회사 고용계약·비밀유지계약이 이 스킬보다 우선합니다.

## new <사이클 이름>

1. **범위 정하기**: 사용자에게 사이클 하나를 고르게 합니다. 기능 하나(F-ID), 프로토타입 하나(PT-ID), 운영 개선 과제 하나(F 폴더), 연구 이관 하나(D01), 릴리스 하나(PRD 8절). 관련 산출물 ID와 ADR을 정합니다.
2. **사실 뽑기**: `python3 automation/scripts/edpm_check.py portfolio --ids <ID들> [--adr <ADR들>]`. 출력은 기간(최초·최종 갱신일), 문서별 상태, 스펙 규모(기능·유저스토리·인수조건·상태 흐름·작업 상태), 미해결 `[가정]`·`[확인 필요]` 수, 게이트 기록(`gate_skip`·`early_draft` 사유), 결정 목록과 적중률, 프로토타입 목록입니다. 필요하면 `git log --format='%ad %s' --date=short -- <파일>`로 날짜를 보탭니다.
3. **재료 읽기**: PRD 1·2·9절, E01·F01·D01(문제 정의), ADR 본문(선택지·이유·예측·결과), E09 3절(대표 기능 하나), V01·V03(가설·결정), A06·`ai_eval.py` 결과(AI 품질), E19·F04·`/edpm-metrics` 결과(결과 지표), E20·F04 회고.
4. **역할 묻기**: 사이클의 각 단계에서 사용자가 한 일을 묻습니다 (주도 / 공동 / 검토 / 참여 안 함). 답을 2절 표에 그대로 씁니다.
5. **초안 작성**: 아래 구조로 `05.outputs/portfolio/<사이클 이름>.md`를 씁니다. 표의 행에 "예시"라는 말을 쓰지 않습니다 (내보내기가 예시 행을 지움).
6. **기밀 점검**: `check`를 실행하고 결과를 보여줍니다.
7. log: `## [YYYY-MM-DD] portfolio | <사이클 이름> — 문서 n건, 결정 n건`.

### 구조

```markdown
---
title: <사이클 이름>
type: portfolio
period: <최초 갱신일> ~ <최종 갱신일>
role: <PM / AI 프로덕트 기획 등>
disclosure: 내부 | 익명화 외부 공유 | 외부 공유 승인됨
updated: YYYY-MM-DD
---

# <사이클 이름>

## 1. 한 줄 요약
<누구의 어떤 문제를> <어떻게 정의하고> <무엇을 만들어 검증했고> <무엇이 달라졌다>. 수치는 portfolio·metrics 출력만.

## 2. 맥락과 나의 역할
| 항목 | 내용 |  (서비스 유형·사용자·팀 구성·기간 — 회사·제품명은 disclosure에 따라)
| 단계 | 나의 역할 | 함께 한 사람(역할) |  (문제 정의 / PRD / 스펙 / 프로토타입 / 개발 합의 / 출시·측정)

## 3. 문제 정의
처음 받은 요청 → 근거(인터뷰·데이터·연구) → 다시 정의한 문제. 바뀐 이유를 적습니다.

## 4. 주요 결정과 이유
| 결정 | 선택지 | 고른 이유 | 예측 | 결과 (적중·빗나감) |
결정 적중률 n건 중 n건. 빗나간 결정에서 배운 것 한 줄.

## 5. 개발이 참조한 산출물
PRD → 요구사항 → 스펙 추적 한 줄, 스펙 규모(기능·유저스토리·인수조건·상태 흐름), 대표 기능 하나의 유저스토리·인수조건·상태 흐름 발췌, 프로토타입(충실도·검증 질문·결정).

## 6. AI 활용과 검증
| 단계 | 쓴 도구 | AI가 한 일 | 내가 확인한 방법 |
- 근거 표시: 사실 주장마다 출처, 근거 없는 문장은 [가정] — 사이클 종료 시 미해결 [가정] n건, [확인 필요] n건
- 순서 지키기: 전제조건 게이트, 건너뛴 경우 사유(게이트 기록)
- AI 기능 품질: 평가셋 크기·합격 기준·결과(A06), 비용·지연 트레이드오프 (해당 시)

## 7. 결과
지표: 기준선 → 결과, 계산 경로(SQL·스크립트). 결과가 없거나 실패했으면 그대로.

## 8. 배운 것과 다음
다시 한다면 바꿀 것 2~3개.
```

## build <파일>

`python3 automation/scripts/edpm_export.py 05.outputs/portfolio/<파일>.md --out-dir 05.outputs/portfolio` → HTML(인쇄하면 PDF). `--to pdf`, `--to docx`도 됩니다. 빌드 전에 `check`를 다시 실행하고, 차단 항목이 있으면 멈춥니다.

## check <파일>

외부로 나갈 수 있는 상태인지 점검합니다. `disclosure`가 `내부`면 1번만 봅니다.

1. **개인정보**: `python3 automation/scripts/edpm_check.py pii <파일>` — 0건이어야 합니다. 학생·교사·보호자 실명, 학교+학년+반 조합도 사람이 확인합니다.
2. **회사 기밀**: 매출·단가·계약 조건·고객사·미공개 로드맵·내부 시스템 이름·원자료 수치. 내부 지표는 상대값("기준선 대비 +n%p")이나 범위로 바꾸고, 그래도 민감하면 뺍니다 (`/edpm-wiki promote` 기준과 같음).
3. **회사·제품 식별**: `disclosure: 익명화 외부 공유`면 회사명·제품명·브랜드·사람 이름을 `grep`해 0건인지 확인합니다. "중견 교육기업의 영어 학습앱"처럼 일반화합니다.
4. **주장 검증**: 1·7절의 모든 수치가 portfolio·metrics 출력이나 산출물에 있는지 대조합니다. 없으면 지웁니다.
5. **역할**: 2절의 "나의 역할"이 사용자가 답한 것과 같은지.

결과는 `통과 / 고칠 것 n건 / 외부 공유 불가 사유` 표로 보여주고, 외부 공유는 사용자가 회사 기준을 확인한 뒤 `disclosure: 외부 공유 승인됨`으로 직접 바꿉니다.

## list

`05.outputs/portfolio/`의 포트폴리오와 `period`, `disclosure`, 마지막 빌드 파일.

## 쓰는 때

- 사이클이 끝났을 때 (V03 결정, F04 효과 리뷰, E20 회고 직후 — 기억이 남아 있을 때)
- 분기·반기 평가, 사내 사례 발표
- 이직 준비: 회사를 떠나기 전에 `/edpm-wiki promote`(일반 지식)와 함께. 포트폴리오는 회사 승인 없이 원문을 가져가지 않습니다.
