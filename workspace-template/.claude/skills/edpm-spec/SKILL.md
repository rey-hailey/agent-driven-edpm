# edpm-spec

**스펙이 곧 지시서이자 계약입니다.** 특히 구현을 LLM이 할 때, 스펙 없이 짠 코드는 그때그때의 판단입니다. 순서: `PRD.md` → E06 REQ·인수조건 → **E09 스펙** → 구현 → 인수조건 = 테스트로 검증 → 바꿀 때는 스펙부터.

게이트: **G-SPEC** — E09가 `done`이기 전에는 제품 코드(`src/`)를 쓰지 않습니다 (PreToolUse 훅이 막음). 검증용 spike는 `06.prototypes/`에 V01과 함께만.

운영 개선 과제의 **F02(기능 기획서)도 기능 단위 스펙**입니다. `check`·`tasks`·`build`는 대상으로 F02 경로를 받으면 F02의 US·AC·상태 흐름(2.1)·계약과 작업(5.1)에 같은 규칙을 적용합니다. 승인된 F02는 G-SPEC에서 E09와 같이 취급됩니다.

`qa` 하위 명령은 같은 폴더의 `qa.md`를 읽고 따릅니다 (B06 테스트 시나리오 → 실행 → 결함 → B07 결과 보고).

## write — E09 스펙 작성

전제: PRD `review` 이상, E06 `done` (G-PRD, 전제조건). 입력: PRD 5·6·7·10절, E06 REQ·AC, E08(학습 활동), E10(화면, 있으면), A10(AI 방식, 있으면), B01(시스템 구조, 있으면).

1. **기능 목록과 추적** (E09 1절): REQ마다 기능 F-ID. 모든 F는 PRD 5절 기능 묶음과 REQ로 거슬러 올라가야 합니다. 거슬러 오르지 못하는 기능은 만들지 않거나 PRD에 먼저 추가합니다.
2. **기능 상세** (3절): 기능마다 **유저스토리 → 인수조건 → 상태 흐름** 순서로 씁니다.
   - 유저스토리(US): "{역할}로서 {목적}을 위해 {행동}하고 싶다", 스토리마다 확인하는 AC.
   - 인수조건: Given/When/Then — 관찰 가능한 결과로.
   - 상태 흐름: 상태가 둘 이상이면 Mermaid `stateDiagram-v2`. 기본·빈·오류·시간 초과·권한 없음·오프라인·사람 이관을 넣고, 상태마다 AC 또는 4절 예외와 연결합니다. AI가 관여하면 E14 2.1 응답 흐름(거절·대체·이관)과 같은 상태 이름을 씁니다.
   - 정적 문서로 설명이 어려운 인터랙션·AI 응답은 `/edpm-proto`로 클릭 프로토타입을 만들어 링크합니다 (컨셉 합의용, 개발 수준 아님).
3. **교육 현장 예외** (4절): 반 이동, 학기 초 일괄 계정, 동의 철회, 시험 기간 동결, 수업 시작 직후 동시 접속, 미성년 데이터 삭제 요청.
4. **입출력·데이터 계약** (6절): 기능 사이·외부 서비스·파일 형식. 필드·타입·단위·예시·검증 방법. 바이브코딩이면 JSON 스키마·폴더 구조까지.
5. **작업 분해와 테스트 추적** (7절): 작업(T) 하나는 하루 이내, AC 하나 이상을 통과시키는 단위. 작업마다 테스트(자동이면 `tests/` 경로, 수동이면 절차). 순서·의존을 적습니다.
6. 사용자 검토 후 `status: review` → 승인 시 `done`. `done`이 되어야 제품 코드가 열립니다.

## check — 추적 점검

`PRD 5절 → REQ → F → US → AC → T → 테스트`에서 끊긴 곳을 표로 보여줍니다: REQ 없는 F, 유저스토리 없는 F, AC 없는 US, T 없는 AC, 테스트 없는 T, PRD에 없는 기능, 상태가 둘 이상인데 상태 흐름이 없는 기능, 상태 흐름의 실패 분기 중 AC·예외와 연결되지 않은 것. 규모는 `edpm_check.py portfolio --ids E09`의 `spec`(기능·유저스토리·인수조건·상태 흐름·작업 수)로 확인합니다. 계약(6절) 없는 기능 간 연결도 표시합니다.

## tasks — 작업 내보내기

E09 7절 작업을 `M02_WBS.csv`에 WP로 넣고(`산출물ID: E09`, 이름 `[T-07] …`), 일정 관리 도구가 GitHub면 `/edpm-wbs push`(승인 후). 개발팀 체계면 `/edpm-handoff dev <대상> --format issues`로 인수조건까지 이슈 본문에.

## build <T-ID> — 작업 구현 (바이브코딩 체계만)

`AGENTS.md` 2절 개발 체계가 **바이브코딩**일 때만 씁니다. 개발팀 체계면 멈추고 `/edpm-handoff dev`를 안내합니다.

1. E09 7절에서 T-ID의 작업·F·AC·테스트, 6절 계약을 읽습니다. PRD 10절 스택을 따릅니다.
2. **테스트 먼저**: AC를 테스트로 씁니다 (`tests/`). 실패하는 것을 확인합니다.
3. `src/`에 구현합니다. 계약(6절)과 다른 형식이 필요하면 멈추고 스펙을 먼저 고칩니다 (`/edpm-spec write`로 6절 갱신, 사용자 승인).
4. 테스트 통과 → E09 7절 상태 `완료`, 커밋 하나 (`[T-07] 힌트 응답 스키마`).
5. 작업 범위를 넘는 개선 아이디어는 구현하지 않고 백로그·PRD 열린 질문으로 보냅니다.

지킬 것: 비밀값은 `.env`(커밋 금지), 실제 학습자 데이터 금지(가상·가명), 라이선스가 기록되지 않은 모델·자산 금지(A10·PRD 7절).

## status

E09 7절 작업의 상태별 개수, 다음에 할 수 있는 작업(의존 충족), 테스트 통과 현황(`tests/` 실행 결과가 있으면).
