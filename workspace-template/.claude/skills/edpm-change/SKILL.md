# edpm-change

원칙: **고친 곳 하나로 끝나지 않습니다.** 산출물 본문이 바뀌면 저장 훅(`edpm_ripple.py record`)이 그 문서를 전제로 쓰는 바로 아래 문서와 같은 ID를 쓰는 문서를 "전파 대기"로 기록하고, 상황판·대시보드에 띄웁니다. 대기 중인 문서를 고치면 그 대기는 풀리고, 이번에는 그 문서의 하위로 전파됩니다. 한 단계씩 이어지므로 PRD를 고치면 E06 → E09 → E10 → 테스트·WBS까지 차례로 닿습니다. 판정은 `automation/scripts/edpm_ripple.py`만 하고, LLM은 무엇을 어떻게 고칠지 제안합니다.

상태(status)만 바꾼 저장, 아직 손대지 않은 템플릿, `n/a` 문서는 전파 대상이 아닙니다.

## status (인자 없음)

1. `python3 automation/scripts/edpm_ripple.py pending`으로 대기 목록을 봅니다.
2. 원천별로 묶어 표로 보여줍니다: 원천 → 확인할 문서, 이유(전제로 씀 / 같은 ID), 기록일.
3. 체인 순서(PRD → E05·E06 → E09 → E10·E12·E13 → B·테스트)로 위에서부터 처리하자고 제안합니다. 아래부터 고치면 위를 고칠 때 다시 고치게 됩니다.

## <문서 경로|ID> — 전파 처리

1. **범위**: `python3 automation/scripts/edpm_ripple.py <문서>`로 하위 산출물·같은 ID를 쓰는 문서·테스트·코드·WBS·화면을 봅니다.
2. **무엇이 바뀌었나**: 원천 문서의 변경을 `git diff -- <원천>`(커밋 전) 또는 직전 커밋과 비교해 요약합니다 — 추가·삭제·이름 변경된 ID, 바뀐 규칙·인수조건·지표.
3. **대상마다 판정** (바로 아래 문서부터):

   | 판정 | 할 일 |
   |------|-------|
   | 고칠 곳 있음 | 바뀐 ID·규칙이 쓰인 절을 짚어 수정안을 보여주고, 승인 후 고칩니다. 저장하면 대기가 풀리고 다음 단계로 전파됩니다 |
   | 고칠 것 없음 | 이유를 한 줄로 말하고 `edpm_ripple.py ack <문서> <사유>` |
   | 결정 필요 | 원천의 변경이 하위 문서의 합의(예: E13 개인정보 판정, P01 환불 규칙)를 바꾸면 사용자에게 묻고, 되돌리기 어려우면 `/edpm-decide new` |

   - `done` 문서를 고치면 내용이 승인 때와 달라집니다. 의미가 바뀌는 수정이면 `status: review`로 내리고 다시 승인받자고 제안합니다. 단 E09·F02(스펙)를 review로 내리면 제품 코드 쓰기가 닫히므로(G-SPEC) 개발이 진행 중이면 사용자에게 먼저 묻습니다.
   - ID 이름을 바꿨으면 같은 ID를 쓰는 모든 문서에서 함께 바꿉니다. 지운 ID를 아직 쓰는 곳은 끊긴 추적입니다.
4. **테스트·코드**: 인수조건이 바뀌었으면 테스트도 바뀌어야 합니다. 커밋된 테스트는 훅이 막으므로(테스트 고정) 스펙을 먼저 고치고 사용자 확인 후 `.edpm/test-unlock`에 `경로 | 사유 | 날짜`를 적습니다. 개발 체계가 개발팀이면 코드는 고치지 않고, 바뀐 인수조건을 `/edpm-handoff dev`로 넘깁니다.
5. **WBS**: `edpm_ripple.py wbs <원천>`으로 전파 작업 후보(`WP-R.n [변경] … 갱신`)를 보여주고, 승인 후 `--write`로 `M02_WBS.csv`에 넣습니다. 이미 완료된 작업에 다시 할 일이 생겼으면 그 작업을 되살리지 않고 변경 작업을 새로 추가합니다(진행 상태의 정본은 일정 관리 도구). 일정이 밀리면 `/edpm-wbs impact`, GitHub 등 도구에 올리는 것은 `/edpm-wbs push`(승인 후).
6. **화면**: 원천이 E10이거나 화면 ID(SCR)가 바뀌었으면 화면 지도는 저장 훅이 다시 만듭니다. sb-lowfi 화면설계서를 쓰고 있으면 `edpm_screens.py --sb-md`로 입력을 다시 만들고 바뀐 화면만 다시 그립니다.
7. **기록**: `02.wiki/log.md`에 `## [YYYY-MM-DD] change | {원천} {요지} → {갱신한 문서}, ack {N}건, WBS {WP-R.n}`. 끝나면 `edpm_ripple.py pending`이 비었는지 확인합니다.

## screen <SCR-ID> [URL|경로] — 화면에서 문서로 역반영

기획·디자이너가 스테이징이나 코드에서 화면을 먼저 고쳤을 때 씁니다. 화면의 기준은 배포된 코드가 될 수 있지만, **규칙(상태·인수조건)의 기준은 문서**입니다. 역반영하지 않으면 다음 구현 때 에이전트가 옛 스펙을 보고 화면을 되돌립니다.

1. **지금 화면 읽기**: URL이면 브라우저 도구(Claude in Chrome 또는 `webapp-testing`)로 화면과 DOM을 읽고, 경로면 `src/`의 해당 화면 코드를 읽습니다. 테스트 계정·가상 데이터만 씁니다. 운영 학습자 화면은 열지 않습니다 (AGENTS.md 7절).
2. **문서와 비교**: E10 8절의 그 화면 블록(영역·항목·버튼·이동·입력), 3절 상태(빈·로딩·오류·동의 없음·오프라인·권한 없음), 연결된 기능(E09 3절 또는 F02 2절)의 인수조건·상태 흐름과 비교해 표로 보여줍니다.

   | 요소 | 문서 | 지금 화면 | 종류 | 제안 |
   |------|------|-----------|------|------|
   | 예: 제출 확인 | SCR-021 하단 `[제출 확인]` | 없음 (바로 제출) | 규칙 | 결정 필요 — 학습 흐름에 닿음(F01 판정 질문) |
   | 예: 버튼 위치 | 하단 | 상단 고정 | 배치 | E10 8절 갱신 |

   - **배치·문구**: E10 8절만 고칩니다.
   - **규칙**(상태·조건·이동·권한): 인수조건이 바뀌는 일이므로 PM이 승인해야 합니다. 승인하면 E09·F02의 AC와 상태 흐름을 고치고, 승인하지 않으면 화면을 되돌리는 결함으로 등록합니다(`/edpm-spec qa defects`).
   - 학습 흐름에 닿는 변경(제출 확인 제거, 힌트 한 번에 펼치기 등)은 사용성처럼 보여도 학습 과제로 판정합니다 (F01 0절).
3. **갱신**: 승인된 것만 문서에 반영합니다. 저장하면 변경 전파가 이어집니다(E10 → 테스트·WBS, E09 → E10·테스트).
4. **기록**: `02.wiki/log.md`에 `## [YYYY-MM-DD] change | screen SCR-021 — 배치 2·규칙 1(승인) 역반영`.

## asbuilt <릴리스> [--code <경로>] — 출시 후 현행화

**출시 전에는 스펙이 기준이고, 출시 후에는 배포된 코드가 기준입니다.** 구현 중에 바뀐 것(화면 경로, API, 기능)을 문서가 따라가지 않으면 다음 릴리스에서 에이전트가 낡은 스펙을 보고 되돌립니다. 차이는 스크립트가 찾고, 판정은 PM이 합니다. E15가 done이면 이 기록과 판정이 있어야 M05·E20을 완료할 수 있습니다 (G-ASBUILT).

1. **대조**: `python3 automation/scripts/edpm_asbuilt.py scan` — 코드 경로는 `--code`, 없으면 AGENTS.md 2절 "제품 코드 위치", 없으면 `src/`. 개발팀 체계면 개발팀 저장소를 읽기 전용으로 지정합니다 (코드는 고치지 않음). 코드를 볼 수 없으면 `record <릴리스> --no-code "사유"`로 기록을 만들고 배포 화면을 `screen`으로 하나씩 대조합니다.
2. **기록**: `edpm_asbuilt.py record <릴리스>` → `05.outputs/현행화/<릴리스>_<날짜>.md` (요약, 차이 표, 일치 목록, 현행화 이력).
3. **판정**: 차이마다 근거를 보여주고 사용자와 함께 `{판정}`을 채웁니다.

   | 판정 | 뜻 | 할 일 |
   |------|----|-------|
   | 문서 갱신 | 코드가 맞다 | 해당 문서(E10 8절 주소·블록, B02 API, E09 기능·AC, F02)를 고칩니다. 저장하면 변경 전파가 이어집니다. 인수조건이 바뀌면 PM 승인 |
   | 결함 | 문서가 맞다 | `/edpm-spec qa defects`로 등록, 개발팀이면 `/edpm-handoff dev` |
   | 의도된 차이 | 둘 다 맞다 | 조치·사유 칸에 이유 (예: 운영자 전용 내부 API, 실험용 숨은 화면) |

   - "코드에만 있는 기능 ID"가 "후속 릴리스"이면 범위가 앞당겨진 것입니다. E09 릴리스 열과 PRD 8절을 함께 고칩니다.
   - 학습 흐름에 닿는 차이(제출 확인 제거 등)는 "문서 갱신"이라도 F01 판정 질문으로 학습 영향을 확인합니다.
4. **이력**: 고친 문서를 기록 끝 "현행화 이력" 표에 적습니다 (변경·추가·삭제 수, 날짜).
5. **이어서**: 화면 아카이브(`archive`)와 함께 하면 그 릴리스의 화면·문서·코드가 한 날짜로 맞춰집니다. 다음 릴리스 스펙(E09 후속 기능, F02)은 이 현행화된 문서에서 시작합니다.
6. **기록**: `02.wiki/log.md`에 `## [YYYY-MM-DD] change | asbuilt R1 — 차이 N (문서 갱신 N, 결함 N, 의도된 차이 N)`.

## archive <릴리스> [기본 URL] — 릴리스 화면 아카이브

출시 배포 후 그 릴리스의 화면을 남깁니다. 손으로 Figma에 옮기는 아카이브는 금방 끊기므로 자동으로 합니다. `/edpm-spec qa smoke`가 끝난 뒤에 이어서 하면 좋습니다.

1. `python3 automation/scripts/edpm_screens.py --archive <릴리스> --base <URL> [--capture]` — `05.outputs/화면아카이브/<릴리스>_<날짜>/index.md`와 화면별 PNG 자리를 만듭니다. 자동 캡처는 E10 8절에 `- 주소:`가 있는 화면만 하며, `--capture`는 Playwright가 설치돼 있을 때 직접 찍습니다.
2. Playwright가 없으면 `webapp-testing` 스킬이나 브라우저 도구로 index의 경로대로 저장하고 같은 명령을 다시 실행해 index를 갱신합니다. 로그인이 필요한 화면은 테스트 계정으로만.
3. 주소가 없는 화면은 E10 8절에 `- 주소:`를 채우자고 제안합니다 (다음 릴리스부터 자동).
4. **Figma에도 남기는 팀이면** (선택): Figma 연결 도구가 있으면 승인 후 아카이브 파일에 `<릴리스> <날짜>` 페이지를 만들고 화면별 캡처를 SCR-ID 이름으로 올립니다. 이 페이지는 기록이며 설계 원본이 아닙니다 — 다음 설계는 E10과 sb-lowfi(필요하면 `sb-lowfi-figma`)에서 시작합니다.
5. 아카이브 폴더는 고치지 않습니다. 다음 릴리스는 새 폴더입니다.
6. **기록**: `02.wiki/log.md`에 `## [YYYY-MM-DD] change | archive R1 — 화면 N개 (캡처 N, 주소 없음 N)`.
