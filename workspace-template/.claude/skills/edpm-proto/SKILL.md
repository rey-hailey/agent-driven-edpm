# edpm-proto

트랙 V(프로토타입·MVP)의 스킬입니다. 흐름과 원칙: 프레임워크 `guide/11.프로토타입과MVP.md`. 신사업(N03 가설)과 운영 개선(F01 문제·F02 기획) 모두에서 씁니다.

원칙:
- **질문 먼저, 만들기는 나중.** 무엇을 알아내려는지(V01 1절) 없이 빌드하지 않습니다.
- **가장 낮은 충실도.** 종이·클릭·오즈의 마법사로 답할 수 있으면 코드를 쓰지 않습니다.
- **기준은 결과 전에.** 성공·중단 기준을 빌드 전에 정하고, 결과를 본 뒤 바꾸지 않습니다 (바꾸면 ADR).
- **timebox.** 기간을 넘기면 범위를 줄입니다.
- **가상 데이터, 버릴 수 있는 코드.** 실제 학습자 데이터는 쓰지 않고, 프로토타입 코드는 운영에 그대로 올리지 않습니다 (G-PROTO).

## new <이름>

1. `03.docs/V.프로토타입/프로토타입목록.csv`에서 다음 PT 번호를 정하고 행을 추가합니다 (상태 `계획`). 예시 행은 첫 실사용 때 지울지 묻습니다.
2. `03.docs/V.프로토타입/{PT-ID}_{이름}/`을 만들고 `_프로토타입템플릿/`의 V01~V03을 복사해 frontmatter `prototype`에 PT-ID를 적습니다.
3. `06.prototypes/{PT-ID}_{이름}/README.md`를 만듭니다 (충실도, 실행 방법, V01·V02 링크).
4. 이어서 `plan`을 진행합니다.

## plan → V01

0. **PRD 9절에서 시작합니다.** 프로토타입은 축소판 PRD가 아니라 PRD가 정의한 제품의 **정수**(핵심 경험, 가장 위험한 가정)를 보여주는 것입니다. `PRD.md` 9절에서 어느 행을 보여줄지 고르고 V01 0절에 적습니다. 9절에 없으면 먼저 `/edpm-prd update`로 추가합니다. PRD가 없으면 멈추고 `/edpm-prd`를 안내합니다.
1. 연결 문서를 찾습니다: 신사업이면 N03의 HY, 운영 개선이면 F01 문제(와 F02 초안). 없으면 무엇을 검증하려는지 한 문장으로 묻습니다.
2. 가장 위험한 가정을 고릅니다: 가치(원하는가), 사용성(쓸 수 있는가), 실현 가능성(만들 수 있는가, AI 품질 포함), 사업성(돈을 내는가, 운영이 되는가), 학습 효과(배우는가).
3. 충실도를 추천합니다. 위험 → 충실도 기본값:

   | 가장 위험한 가정 | 먼저 시도할 충실도 |
   |------------------|--------------------|
   | 흐름을 이해하는가 | P0 |
   | 화면을 쓸 수 있는가, 가치 제안에 반응하는가 | P1 |
   | 진짜 결과를 받으면 행동이 바뀌는가 (AI·자동화 전) | P2 |
   | AI 답 품질이 쓸 만한가 | P3 (`/edpm-ai nocode`, 골든셋 10개) |
   | 실제 사용·재방문·학습 신호 | P4 |

4. 범위(진짜·가짜·안 만듦), 성공·중단 기준, 참여자·과제 시나리오, timebox, 데이터·안전, (P3·P4면) 빌드 환경을 채웁니다. 수치 기준이 없으면 `[가정]`으로 두고 사람이 정하게 합니다.
5. timebox를 WBS WP로 넣을지 묻고 `/edpm-wbs`에 반영합니다.
6. 미성년이 참여하면 E13 핵심 항목(동의, 최소 수집, 외부 AI 전송)을 확인하고, 보호자 동의서 초안을 `06.prototypes/{PT}/ops/동의서.md`로 만듭니다.

## build → V02 (G-PROTO: V01 4·6·7절 확정 후)

충실도별로 실제 결과물을 만듭니다. 결과물은 `06.prototypes/{PT}/`에 둡니다.

| 충실도 | 만드는 방법 |
|--------|-------------|
| P0 | E10 또는 V01 범위로 화면 흐름 ASCII 배치를 쓰고 `sb-lowfi-pptx`로 와이어프레임 PPTX·HTML 생성 |
| P1 | `06.prototypes/_starter/click-prototype.html`을 복사해 화면(`<section class="screen" id="SCR-xxx">`)을 채움. 측정할 행동에 `data-event`를 붙임. 개발 전달용이면 `sb-lowfi-pptx`(low-fi 와이어프레임 HTML·편집 가능한 PPTX), Figma가 필요하면 `sb-lowfi-figma` 또는 Figma 연결 도구 |
| P2 | P1 화면 + `ops/운영스크립트.md`(뒤에서 처리하는 사람의 절차, 응답 기준·템플릿, 응답 시간 목표, 근무표, 실수했을 때 대처). 참여자에게 사람이 처리한다는 사실을 어떻게 알릴지 V01 7절에 따라 정함 |
| P3 | Google Forms·Sheets 흐름, n8n 워크플로(`n8n-*` 스킬), AI면 `/edpm-ai nocode`과 `/edpm-ai eval`로 골든셋 10개 확인 |
| P4 | 아래 "코드 MVP" 절차 |

### 코드 MVP (P4)

1. **스택**: `AGENTS.md` 2절 회사 스택을 따릅니다. 없으면 기본값 Next.js(App Router) + Tailwind CSS + Supabase(PostgreSQL, 인증·스토리지) + Vercel. AI 기능은 서버 쪽 라우트에서 Claude API를 부르고(키는 서버에만), 방식 선택은 A10 원칙(규칙·검색이 되면 LLM을 쓰지 않음)을 따릅니다.
2. **위치**: 프로토타입 코드는 항상 `06.prototypes/{PT}/app/`(제품 코드 `src/`가 아님 — `src/`는 스펙 승인 후 G-SPEC). 프로토타입을 제품으로 키우지 않습니다. 제품은 E09 스펙에서 다시 시작합니다(개발팀: `/edpm-handoff dev`, 바이브코딩: `/edpm-spec build`). 개발자와 함께 하거나 배포가 길어지면 별도 저장소(비공개)를 만들고 V02에 URL을 적습니다.
3. **순서**: 핵심 흐름 하나를 끝까지 동작시키기 → 가상 데이터 시드 → V01 신호를 재는 최소 이벤트 로그(테이블 하나: 시각, 참여자 ID, 이벤트, 값) → 접근 제한 배포 → 리허설. 기능을 넓히기 전에 핵심 흐름부터.
4. **커밋**: 작은 단위로 커밋하고, 세션마다 진행을 V02 1·2절에 적습니다.
5. **지킬 것**: 비밀값은 `.env.local`(커밋 금지), 실결제 금지(테스트 모드), 공개 URL 접근 제한·검색 차단, 실제 학습자 데이터 금지, 외부 API로 학생 원문을 보내지 않음(가명·가상 데이터).
6. **점검**: 테스트 전에 `webapp-testing`(Playwright)으로 핵심 시나리오 스모크를 돌립니다. 챗봇·튜터의 답 품질은 `/edpm-ai eval`(골든셋·시나리오셋)로 따로 봅니다.

빌드가 끝나면 V02를 채웁니다. 특히 5절 "알려진 한계"(운영에서 다시 만들어야 할 것)를 빠뜨리지 않습니다.

## test — 사용자 테스트

1. `06.prototypes/{PT}/ops/`에 진행 자료를 만듭니다: 진행자 스크립트(소개 → 사전 질문 → 과제 2~4개 → 사후 질문, 정답 경로를 알려주지 않음), 관찰 기록지(과제별 성공·막힌 지점·인용), 사후 설문(V01 신호에 맞춘 문항).
2. 미성년이면 동의서 회수, 보호자 동석, 세션 시간 상한(예: 20~30분)을 확인합니다.
3. 세션 후 관찰 기록·이벤트 로그(클릭 프로토타입은 "기록 → CSV 내보내기")를 `00.inbox/`에 넣고 `/edpm-wiki ingest`로 가명 처리해 `01.자료실/현장/`·`데이터/`에 보관합니다.
4. 세션마다 짧게 중간 정리합니다 (치명적 문제가 반복되면 남은 세션 전에 고칠지 묻되, 고치면 V03에 기록).

## decide → V03

1. V01 기준표 그대로 결과를 채우고 판정합니다. 계산은 스크립트로 하고 표본이 작으면 그렇게 적습니다.
2. 발견을 심각도와 근거(가명 인용)로 정리합니다.
3. 결정을 제안합니다: 폐기 / 재검증(바꿀 것 하나) / MVP 확장(다음 위험을 더 높은 충실도로) / 개발 이관. 결정은 사람이 하고 ADR로 남길지 묻습니다.
4. **아직 모르는 것**: 이번 테스트로 답하지 못한 것과 새로 생긴 질문을 V03 "아직 모르는 것" 표에 적고, 각각 넘길 곳(PRD 12절 열린 질문, 다음 가설·프로토타입, 백로그, ADR)에 실제로 옮긴 뒤 넘긴 곳 칸을 채웁니다. 빈 칸은 상황판이 계속 보여줍니다.
4. 반영: N03 가설 판정(신사업) 또는 F02 범위·US(운영 개선), 위키 `research/`에 인사이트(IN-ID), 프로토타입목록.csv 상태·결정.
5. 정리: 테스트가 끝난 배포를 내리고 참여자 데이터 파기 일정을 확인합니다.

## handoff — 개발 이관

V03 6절 이관 패키지를 채우고, 갱신할 문서를 하나씩 제안합니다: E06 REQ, E09 기능, E10 화면(와이어프레임), F02 US·AC, E13(개인정보), B01·B04(운영 구조로 다시 설계할 부분). 프로토타입 코드는 "재사용 / 참고만 / 버림"으로 나누고, 운영 출시는 E15·게이트를 거친다고 안내합니다 (G-PROTO). WBS에 이관 WP를 추가할지 묻습니다.
