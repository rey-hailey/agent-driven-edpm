# edpm-ai-design

E14(AI학습기능설계서)가 "AI가 교육적으로 무엇을 해야 하는가"를 정하고, 이 스킬은 A 트랙으로 "어떻게 만드는가"를 설계합니다. 평가 실행은 `/edpm-eval`이 합니다.

## 원칙

- **조회·계산은 코드, 설명·생성은 LLM.** 명단, 점수, 정답률, 날짜, 출결은 SQL 도구로 가져오고 벡터 검색이나 LLM 추론에 맡기지 않습니다.
- **모든 것을 벡터 DB에 넣지 않습니다.** 교과 설명·해설·FAQ처럼 문장으로 된 지식만 검색 대상으로 둡니다.
- **학습자 데이터 최소화.** LLM에 보내는 것은 그 요청에 필요한 최소한이며, 실명 대신 가명 키를 씁니다 (E13 연결).
- **교육과정 정보는 KG에서.** 성취기준·선수 관계는 교육과정 지식그래프(`automation/kg/kg.db`)를 SQL 도구로 조회합니다. LLM이 성취기준을 지어내지 않게 합니다 (A01·A02·A05 "교육과정 지식그래프 연결" 절).
- **교사 검토.** 학생에게 배포되는 생성물(워크시트, 리포트)은 교사 승인 후 나갑니다.

## opportunity — A00 AI 적용 기회 맵

E14보다 먼저, 서비스 전체 가치사슬(콘텐츠 제작, 학습, 평가, 운영, 영업·마케팅, 교사·강사 지원)에서 AI를 쓸 곳을 고릅니다. 기회마다 가치·실현 가능성·데이터 준비도·위험(교육적·법적: K-12 학생 평가는 AI 기본법 고영향 검토)을 점수화하고, 방법(LLM / 고전 ML / 규칙 / 사람)을 정합니다. 선택된 기회는 E14(학습 기능), A07(자막·번역), A08(문항 생성), A09(이탈 예측)로 넘깁니다. "AI를 쓰지 않는 결정"도 기록합니다. 참고: [[domain/AI적용기회맵]].

## A07~A09 — 콘텐츠·운영 AI

| 산출물 | 핵심 | 평가 |
|--------|------|------|
| A07 자동자막·번역 | 용어 사전, 사람 검수 단계, 음성 복제 동의(P02), 접근성 품질 | 오류율(WER)·검수 시간, 샘플 사람 평가 |
| A08 문항 자동 생성 | 성취기준·오개념 입력(`kg_query.py seed`), 정답 코드 검증, 교과 전문가 검수, 출제 후 문항 분석(SQL) | 검수 통과율, `/edpm-eval`(E14 평가세트·골든셋) |
| A09 학습 이탈 예측 | 라벨·예측 시점 정의, 이벤트 기반 특징(SQL), 규칙·로지스틱 기준선 먼저, 개입 설계와 A/B | 개입 용량 K에서 정밀도·재현율, 집단별 성능 차이 — **LLM으로 예측하지 않음** |

## method — A10 AI 방식 선택·아키텍처

LLM부터 고르지 않습니다. 기능마다 프레임워크 `guide/10.AI방식선택.md`의 스펙트럼(M1 규칙·템플릿, M2 고전 NLP, M3 검색·FAQ, M4 RAG, M5 소형·파인튜닝, M6 로컬·온프레미스 LLM, M7 클라우드 LLM, M8 혼합)에서 **요구를 충족하는 가장 단순한 방식**을 고릅니다.
1. E14의 AI 기능(AI-ID)마다 판단 기준(정확성·결정성, 설명 가능성, 데이터 민감도, 지연, 비용, 오프라인·망, 품질 격차, 운영 역량, 라이선스)을 채우고 결정 MD-ID를 남깁니다.
2. 정답이 정해진 일(채점·출결·진도·점수)은 M1·SQL로 보냅니다. 학생 원문·음성이 외부로 나갈 수 없으면 M6 또는 가명화를 택합니다.
3. 후보가 둘 이상이면 같은 평가셋으로 비교합니다: `ai_eval.py --target claude|local|cmd --label <이름>` (`/edpm-eval compare`).
4. 전체 구성도(계단식: 의도 분류 → FAQ → RAG → LLM, 민감 요청 → 로컬)와 학생 데이터 흐름을 그립니다.

## route — A11 모델 선택·라우팅

평가 결과(합격률·점수·지연 p50/p95·요청당 비용)로 후보 모델을 비교하고, 작업 유형·난이도·데이터 민감도·비용 한도·사용자 등급에 따른 라우팅 규칙(RT-ID), 대체 경로와 시간 제한, 모델 버전 고정·교체 절차를 정합니다. 리더보드가 아니라 우리 평가셋 결과로 고릅니다.

## cost — A12 AI 비용·과금

`python automation/scripts/ai_cost.py --example`로 설정 틀을 만들고, 학습자 수·사용량·요청당 토큰·라우팅 비율·캐시 적중률·FAQ 처리율·로컬 GPU 단가를 채워 `03.docs/A.AI/ai_cost_config.json`에 저장한 뒤 `--config`로 실행합니다. 결과(월 원가, 학습자당 원가, 가격 대비 비중)를 A12에 붙이고, 절감 수단(캐싱, 작은 모델 라우팅, FAQ 처리, 맥락 축소, 배치)과 사용자 과금(포함량·크레딧·요금제)을 S03·S06과 맞춥니다. 가격표(`model_prices.json`)는 공식 페이지에서 다시 확인합니다.

## ops — A13 AI 운영 (MLOps·LLMOps)

버전 관리 대상(데이터, 프롬프트, 모델, 가드레일 규칙, 평가셋), 프롬프트·모델 변경 시 평가 자동 실행(`ai_eval.py`, 합격 기준 미달이면 배포 중단), 배포·롤백, 모니터링 지표(OP-ID: 표본 품질, 환각 신고, 지연, 오류율, 비용, 고전 ML 드리프트, 검색 적중률), 사람 검토 대기열, 장애 대응, 로컬 모델 서빙·갱신, 재학습 주기를 정합니다. 작은 팀 기준으로 시작합니다.

## guardrail — A14 가드레일

입력(개인정보 감지·마스킹, 탈옥·프롬프트 주입, 주제·연령 제한) → 검색(학년·과목·권한 범위) → 출력(안전 분류, 근거 확인, 튜터의 정답 노출 방지, 형식 검증) → 연결(교사·상담 연결, 위기 신호) 단계별로 GD-ID를 정하고, 각 가드레일을 규칙·분류기·LLM 판정·사람 중 어떤 층으로 구현할지 정합니다. 레드팀 세트를 평가셋에 넣어 `/edpm-eval`로 확인하고, 운영 기준은 P08로 넘깁니다. 프롬프트 한 줄로 가드레일을 대신하지 않습니다.

## type — 역할·구성 요소 판정

E14의 AI 기능(AI-01…)마다 두 축을 정합니다.

**교육적 역할 `ai_role`** — 이 AI가 학습에서 하는 일 (여럿 가능)

| 코드 | 역할 | 예 |
|------|------|----|
| T | 튜터·설명 | AI 튜터, 오답 단계별 힌트, 개념 설명, 학습 버디 대화 |
| F | 피드백·채점 | 서술형·말하기·코드 채점과 피드백 |
| G | 콘텐츠·문항 생성 | 문항 생성, 교사 수업 자료, 학부모 리포트 초안, 자막 |
| P | 예측·추천 | 이탈 위험, 숙달 추정, 다음 학습 추천 |
| O | 운영 보조 | CS 답변, 관리자 업무 보조, 검색 |

**구성 요소 `ai_parts`** — 어떤 설계 문서가 필요한지 정함 (다음을 묻고 예인 것을 모두 나열)

| 질문 | 예이면 |
|------|--------|
| 정해진 자료(교과서·해설·규정·FAQ)를 찾아 근거로 답해야 하는가? | `근거` → A01, A02 |
| 학습자의 이전 오류·숙달·선호를 세션 너머 이어 써야 하는가? | `학습자상태` → A04 (+A02 기억 저장소) |
| 서비스 데이터(성적·출결·진도)를 도구로 조회·계산해 써야 하는가? | `데이터조회` → A05 (+A02 도구 연결) |
| 학습자·교사에게 그대로 나가는 결과물을 만드는가? | `생성물` → A05, (문항이면) A08 |
| LLM이 문장을 생성해 사람과 주고받는가? | `대화` → A03 |

모든 AI 기능은 A10 방식 선택, A14 가드레일, A06 평가를 공통으로 거칩니다. 예측 모델(P)은 A09로 갑니다. 섞인 경우는 구성 요소를 나열합니다(예: `근거 + 학습자상태`).

해당하지 않는 산출물은 frontmatter `status: n/a`와 사유를 적습니다. 결과를 E14와 A01~A05의 `ai_role`·`ai_parts`에 반영합니다.

## A01~A05 — 산출물 작성

`/edpm-doc`과 같은 게이트·근거 규칙으로 작성합니다. 산출물별 핵심:

| 산출물 | 먼저 확인할 것 |
|--------|----------------|
| A01 지식베이스 | 소스마다 저작권·이용허락 상태 ([[domain/교육저작권]]), 학년·단원 메타데이터, 학생 표현 사전 |
| A02 검색·RAG | 학년·단원 필터로 범위 밖 내용 차단, 근거 없을 때 거절, 지연·비용 예산 |
| A03 프롬프트·대화 | 시도 전 정답 금지, 힌트 사다리, 위기 신호 고정 응답, 프롬프트 버전 기록 |
| A04 학습자 메모리 | 기억하지 않을 것 목록, 보호자 열람·삭제, 만료 규칙 |
| A05 도구·생성물 | 도구 권한 범위(자기 반만), 학생별 생성 시 그 학생 데이터만, 승인 흐름 |

## goldenset / scenarioset

- `goldenset`: 정답형 평가셋(질문 한 번 → 기대 답·근거·필수 포함·금지 내용)입니다. `kg_query.py seed <코드>`의 평가 예시·오개념(초안)을 출발점으로 삼고, A01의 지식 소스와 E05 학습 목표에서 질문-기대답변 쌍을 뽑아 `03.docs/A.AI/골든셋.csv`에 추가합니다. 쉬운 질문만 만들지 않도록 유형을 섞습니다: 개념 설명, 풀이 해설, 오개념 교정, 범위 밖 질문, 학생식 표현, 정답만 요구, 근거 없는 질문(거절해야 함). 목표 30건 이상.
- `scenarioset`: 시나리오형 평가셋(사전 상태와 여러 턴 → 기대 행동)입니다. `학습자상태`는 세션을 넘는 이어 쓰기 확인(지난주 틀린 유형을 기억하는가, 기억하면 안 되는 정보를 기억하지 않는가), `데이터조회`·`생성물`은 교사 요청부터 승인까지 흐름을 `시나리오셋.csv`에 씁니다. 목표 10건 이상.
- 초안은 사람이 검토합니다. 교과 정답은 교과 전문가가 확인할 때까지 비고에 `검토 전`을 적습니다.

## nocode — P3 노코드 점검

코드를 쓰기 전에(P4 코드 MVP 전에), 지식 문서 몇 개를 통째로 넣고 골든셋 10개로 답이 쓸 만한지 봅니다.
- 가장 빠른 방법: `/edpm-eval --context <지식 문서>`로 검색 없이 문서 전체를 시스템 프롬프트에 붙여 평가 (구성 요소 `근거`만, 문서가 작을 때)
- 또는 Claude 프로젝트·NotebookLM에 문서를 올리고 질문 10개를 직접 해보기
- 결과를 A01 "P3 노코드 점검" 절에 기록합니다. 여기서 대부분 틀리면 검색 설계 전에 지식 소스부터 고칩니다.

## prompt-export

A03의 시스템 프롬프트를 `03.docs/A.AI/prompts/system_vN.md`로 분리 저장합니다. `/edpm-eval --system`이 이 파일을 씁니다. 버전을 올릴 때마다 A03 "프롬프트 변경 이력"에 PR-ID, 바꾼 이유, 평가 결과 링크를 남깁니다.
