# edpm-handoff

원칙: **같은 사실, 다른 언어.** 근거 산출물은 하나이고, 받는 사람마다 필요한 부분만 그 사람의 단어로 옮깁니다. 새로운 사실을 만들지 않으며, 수치는 `/edpm-metrics` 결과만, 효과 주장은 E19·E17·V03 근거와 증거 수준만 씁니다. 결과는 `05.outputs/handoff_<역할>_<대상>_YYYYMMDD_HHMM.md`, 전달 기록은 `02.wiki/log.md`에 `## [YYYY-MM-DD] handoff | <역할> <대상>`.

## 공통 절차

1. 대상(과제 폴더 `F.개선/202610_…`, `PT-01`, `E09`, `N02` 등)의 산출물과 상태를 읽습니다. `review`·`draft`가 섞여 있으면 패키지 첫 줄에 "확정 아님: …"을 적습니다.
2. 역할별 표(아래)의 순서로 씁니다. 근거 문서의 ID와 절을 각 항목 끝에 `(F02 2절)`처럼 답니다. 받는 사람이 원문으로 거슬러 올라갈 수 있게.
3. 받는 사람이 **결정하거나 답해야 할 것**을 마지막에 질문 목록으로 둡니다 (기한 포함).
4. 개인정보·기밀 점검: 외부(고객·협력사)로 가는 패키지면 회사 기밀 수치·다른 고객 이름을 빼고 그 사실을 알립니다.
5. `--format`이 있으면 변환합니다 (docx·pptx 스킬, `issues`는 개발 패키지를 GitHub 이슈로 — `wbs_sync.py`와 같은 승인 절차).

## dev — 개발자·개발 리드

| 순서 | 내용 | 근거 |
|------|------|------|
| 0 | 제품 전체 맥락: PRD 1·5·8절 (이 작업이 제품의 어디인가, 어느 릴리스인가) | `PRD.md` |
| 1 | 한 줄 목적과 **왜**(문제·근거 규모) | F01, E06 |
| 2 | 범위: 이번에 하는 것 / 하지 않는 것 | F02, N03, V03 |
| 3 | 사용자 스토리와 인수조건 (Given/When/Then), 기능 ID | F02 2절, E09 |
| 4 | 화면·상태 (기본·빈·오류·권한 없음·오프라인), 와이어프레임 링크 | E10 3절, `sb-*` 결과 |
| 5 | 데이터·이벤트 (EV-ID, 개인정보 등급), 계산 규칙 (진도·수료·환불·점수 공식) | E12, L03, P01 |
| 6 | **교육 현장 엣지 케이스**: 시험 기간 동결, 학기 초 계정 일괄 생성, 반 이동·전학, 보호자 동의 철회, 미성년 데이터 삭제 요청, 동시 접속 피크(수업 시작 5분) | E09 4절, E13 |
| 7 | AI가 있으면: 방식(A10), 가드레일(A14), 평가 기준·골든셋 위치(A06), 비용 상한(A12) | A 트랙 |
| 8 | 측정: 출시 전 심어야 할 이벤트, 목표 지표 SQL 경로 (G-MEASURE) | F02 1절, `automation/sql/` |
| 9 | 프로토타입이 있으면: 재사용 / 참고만 / 버림, 다시 만들 것 (G-PROTO) | V02 5절, V03 6절 |
| 10 | 일정·의존성, 출시 제약(시즌) | M02, F03, E15 |
| 11 | 개발팀이 답할 질문 (추정 공수, 기술 위험, 대안) | — |

`--format issues`: 스토리마다 이슈 하나(본문 = 인수조건 + 근거 링크, 라벨 `산출물:F02` 등). 만들기 전 건수를 보여주고 승인받습니다.

## exec — C레벨·결정권자

한 장. 3분 안에 읽히게. `/edpm-report exec`보다 특정 결정 하나에 집중합니다.

| 순서 | 내용 |
|------|------|
| 1 | **결론 한 문장과 결정 요청** (무엇을, 언제까지, 누가) |
| 2 | 왜 지금: 근거 수치 3개 이내 (SQL 결과만, 기준선 대비) |
| 3 | 선택지와 권고 (현상 유지 포함), 각 안의 비용·학습자 영향·되돌릴 수 있는가 |
| 4 | 위험 1~2개와 조기 신호, 중단 기준 |
| 5 | 예측: 맞다면 N주 뒤 보일 것 (`/edpm-decide`의 prediction) |
| 6 | 부록 링크: ADR, N02·F02·V03, 사전 부검 |

결정이 나면 `/edpm-decide new`로 ADR을 만들고 결정자·일자를 기록합니다.

## cs — CS·운영

바뀌는 기능의 FAQ, 예상 문의와 답변 스크립트, 환불·정책 변경점(P01·P05), 장애·롤백 시 안내 문구, 에스컬레이션 기준, 출시 일정. 미성년·보호자 문의는 별도 문구.

## content — 콘텐츠·교육 전문가 (교사 자문, 집필·감수)

학습 목표와 성취기준(E05, KG 코드), 문항·콘텐츠 유형과 제작량(E11, `kg_query.py coverage`), AI 생성물이면 검수 기준(A08, A06), 감수 일정(M02), 저작권·권리(P02).

## legal — 법무·개인정보·보안 검토자

수집 항목과 목적, 미성년·보호자 동의, 보관·파기, 외부 전송(AI API·위탁), 고지 문구, 관련 법령 목록과 `[확인 필요]` 항목 (E13, P01·P07·P09, `/edpm-policy legal-check`). 검토 결과를 받을 양식(항목별 승인·보완·차단).

## feedback <역할> <파일·붙여넣기>

받은 피드백을 워크스페이스로 되돌립니다. 원문은 가명 처리해 `/edpm-ingest`.

| 피드백 | 가는 곳 |
|--------|---------|
| 개발: 공수·기술 위험·대안 | M02(WBS), M03(위험), F02 의존성, 필요하면 ADR |
| 디자인: 흐름 변경, 테스트 필요 | E10, `/edpm-proto` |
| 영업: 고객 반응·거절 사유·새 요청 | `/edpm-feature intake`(백로그), S04 5절 반론, `research/` |
| 경영진: 결정·조건 | `/edpm-decide new`, N04·F03 |
| CS: 반복 문의 | 백로그, P05 |
| 콘텐츠: 오류·난이도 | E11, A06 재평가 |
| 법무: 보완·차단 | E13 판정, 게이트 (차단이면 G-SAFE) |

피드백 반영 후 영향받은 산출물을 `review`로 되돌릴지 묻습니다.
