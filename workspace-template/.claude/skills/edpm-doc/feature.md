# edpm-doc feature

업무 모드 F(운영 개선)의 스킬입니다. 흐름과 원칙: 프레임워크 `guide/09.업무모드.md`. 운영 중 서비스 전체는 루트 `PRD.md`가 정의하고(F00과 함께 현재 상태 반영), 과제마다 F01은 문제, **F02는 기능 단위 PRD·스펙**입니다. 과제가 서비스 범위·목표를 바꾸면 PRD를 갱신합니다. 바이브코딩 체계면 F02 승인 후 `/edpm-spec build`로 구현합니다. 문서는 가볍게(과제당 한두 쪽씩), 영향 점검과 효과 측정은 엄격하게 합니다.

## baseline → F00

운영 중 서비스에 합류했거나 반기마다 실행합니다.
1. 회사 자료(`01.자료실/회사/`, `기술/`, `데이터/`)와 위키를 읽고 F00을 채웁니다: 서비스 요약·유형, 사용자·이해관계자, 기준선 지표(SQL 경로·날짜), 기능 지도, 알려진 문제·VOC 주제, 기술 제약, **깨지면 안 되는 기준**(환불 P01, 진도·수료 L03, 개인정보 E13, AI 평가 A06, 교육과정 매핑 E11 등이 어디 있는지).
2. 기준 문서가 회사에 없으면 무엇을 먼저 만들지 제안합니다 (예: 환불 기준이 문서화되지 않았다 → `/edpm-doc policy P01`).
3. E 체인 중 F00이 대체하는 산출물을 `status: n/a`(사유: 운영 중 서비스: F00이 대체)로 바꾸는 목록을 보여주고 승인받습니다.

## intake — 요청 접수

CS 문의, VOC, 교사·강사·학부모·기관 요청, 영업 요청, 데이터 이상, 회의록에서 요청을 모읍니다.
1. 원문은 `/edpm-wiki ingest`로 자료실·위키에 넣습니다 (개인정보 가명 처리).
2. 요청마다 "누가 어떤 상황에서 무엇을 못 하나"로 바꿔 `03.docs/F.개선/개선백로그.csv`에 FI-ID를 붙여 추가합니다. 같은 문제의 요청은 합치고 근거(건수, 링크)를 늘립니다.
3. "기능 요청"이 아니라 "문제"로 적습니다. 해결안은 비고에 후보로만 둡니다.

## prioritize — 우선순위

백로그 점수: `(도달 × 가치 × 교육적 효과) ÷ (노력 × 위험)` (회사 기준에 맞게 바꿀 수 있음, F00에 기록).
- 도달은 데이터(SQL)로, 가치·교육적 효과는 근거(위키 research/)로 매깁니다. 근거 없는 점수는 `[가정]`.
- 위험에는 정책 영향(환불·정산·개인정보·AI)이 큰 과제를 높게 줍니다.
- 상위 과제와 함께 "이번에 하지 않는 것과 이유"를 보여주고 결정은 사람이 합니다. 결정은 ADR로 남길지 묻습니다.

## new <과제명> → F01

1. `03.docs/F.개선/{YYYYMM}_{과제명}/`을 만들고 `_과제템플릿/`의 F01~F04를 복사합니다. frontmatter `initiative`에 FI-ID를 적습니다.
2. F01을 씁니다: 요청 원문 → 재정의한 문제, 영향받는 이해관계자, 근거(VOC 건수·데이터 SQL·인터뷰), 규모, 현재 우회 방법, **지금의 규칙과 개념(6.1: 고칠 기능이 지금 어떤 규칙·계산으로 돌아가는지, F00 7절·L03·P01·코드에서 확인)**, 성공의 정의, 하지 않을 것. 완료 전에 `edpm_check.py clarity <F01 경로>`로 명확도를 봅니다 — 운영 중 서비스는 맥락(F00 현황 진단, 지금의 규칙)이 가중치가 가장 크고, 모호도 0.3을 넘으면 F01을 done으로 올리지 못합니다 (G-CLEAR).
3. 근거가 약하면 먼저 확인할 것(데이터 쿼리, 사용자 3명 통화)을 제안합니다.
4. 백로그 상태를 `진행`, 과제폴더를 기록합니다.

## spec → F02 (G-IMPACT, G-MEASURE)

1. 목표 지표: 기준선(SQL로 지금 계산)·목표·측정 기간. 학습 지표가 하나 이상 있게 합니다 (가능하면).
2. 사용자 스토리 US-ID와 Given/When/Then 인수조건, 상태 흐름(2.1), 화면 변경(전·후, E10 패턴 참고, 필요하면 `sb-lowfi-pptx`로 와이어프레임), 데이터·이벤트 변경(E12), 입출력 계약과 작업 분해(5.1). F02는 개발팀이 프로토타입이 아니라 이 문서를 기준으로 구현하는 기능 단위 스펙입니다. 화면 구조가 바뀌면 E10(IA)을, 제품 전체 기능 목록이 바뀌면 E09 1절을 함께 갱신합니다.
3. **영향 점검표**를 하나씩 판단합니다. 해당하면 기준 문서를 함께 갱신합니다:

   | 영향 | 갱신할 기준 문서 | 도구 |
   |------|------------------|------|
   | 개인정보·미성년 | E13 | `/edpm-doc E13 --update` |
   | AI 기능·평가 | E14, A06 | `/edpm-ai eval run` 재평가 |
   | 가격·환불·정산 | P01, S07 | `/edpm-doc policy sync P01` |
   | 진도·수료·평가 규칙 | L03, L04 | `/edpm-doc L03 --update` |
   | 교육과정 콘텐츠 | E11 매핑 | `/edpm-curriculum coverage` |
   | 접근성 | E13 (c), B05 | |
   | 콘텐츠 권리 | P02 | |
   | CS·공지 | P05 | |
   | 시즌 타이밍 | G-CAL | 학사일정·기업 예산·성수기 |

4. 영향 항목이 남아 있으면 F03을 완료할 수 없다고 알립니다 (G-IMPACT).
4-1. 해결안이 사용자가 쓸 수 있을지·원할지 불확실하면 개발 전에 `/edpm-proto new`로 프로토타입(P1 클릭, P2 오즈의 마법사 등)을 만들어 검증하자고 제안합니다. V03 결과로 F02 범위·US를 확정합니다.
5. 개발 협업용 요약(스토리·인수조건·이벤트)을 회사 이슈 트래커 형식으로 내보낼지 묻습니다 (`/edpm-wbs export`와 같은 방식, 생성은 승인 후).

## launch → F03

A/B 또는 단계 출시 설계(무작위 단위: 학생·반·학원·기관, 표본·기간 근거), 주 지표·가드레일(학습 지표, 민원율, 환불률), 기능 플래그 단계와 중단 기준, 공지·교사/강사·학부모 안내·CS 스크립트, 시즌 확인, 롤백 계획. 미성년·학습 결과를 대상으로 한 실험이면 이로운 학습을 빼앗지 않는 설계와 동의 필요 여부를 적습니다.

## review → F04 (G-MEASURE)

출시 후 정한 기간이 지나면 F02와 **같은 SQL**로 지표를 계산하고, 가드레일·VOC·이해관계자 반응을 정리해 결정(유지·개선·롤백)을 제안합니다. 결정은 ADR, 배운 것은 위키(research/ 또는 company/), 다음 과제는 백로그로 보냅니다.
